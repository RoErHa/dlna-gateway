Part I · Audit · closed 12 July 2026

Library-completeness audit

How much of the music on disk does the gateway actually serve, and did anything go missing in the move off AssetUPnP? Answer: 236 files were invisible and 10,859 metadata corrections were silently dead. Both were fixed the same day; this part is the record.

Finding 1 · Index coverage

236 files on disk were invisible to the gateway

The LocalFs backend serves the same music root AssetUPnP did, so completeness is simply disk versus index: 26,129 audio files on disk, 25,893 rows in tracks. The missing 236 were all swallowed at insert time by the wide uniqueness constraint UNIQUE(udn, artist, album, title, bit_depth, sample_rate) — built to dedup AssetUPnP’s virtual-album aliases, but for LocalFs it silently dropped any file whose tags collided with a file in another folder: duplicate-edition folders (deluxe vs. standard) and scene compilations sharing tag tuples.

A beets retag was tried first and failed structurally. All 33 collision folders came back “Skipping.”: chroma fingerprint lookups were rate-limited to zero candidates, and what text matching found (correct releases, wrong editions — a 2018 expanded pressing against MusicBrainz’s standard ones) never reached quiet-mode’s strong-match bar. The scene compilations aren’t on MusicBrainz at all.

The fix was architectural instead: the folder identity (album_key) joined the UNIQUE, so two genuinely distinct files in different folders both index. Per-file uniqueness was already idx_tracks_udn_url’s job and browse-level dupe-hiding already _dedup_clause’s — the constraint had been doing display work at the wrong layer. UPnP rows keep album_key='', so their behaviour is unchanged. After the migration, a force rescan brought the index from 25,893 to 26,051 rows — In Absentia (Remastered), the audit’s poster child for a partial album, is complete again.

The remaining 78 collide within a single folder: alternate takes tagged identically (Badfinger’s expanded edition carries original and 2018 mixes of the same songs), disc-subfolder folding putting two “Jamming”s under one album key, and untagged “NN Track.flac” junk. No index constraint can tell those apart — only real retagging can (an interactive beets --timid session), if it’s ever worth an evening.

Finding 2 · Metadata overrides

10,859 of 10,890 manual overrides were silently dead

The biggest surprise. Metadata overrides are keyed by exact track URL — and 10,810 still pointed at AssetUPnP’s :26125 URLs (dead since the decommission) plus 49 at the pre-cutover :8201 port. Among them: the ~10k original-release-year corrections from the 10-hour improve_song_years MusicBrainz sweep. Only 31 manual overrides were actually live. The “1979, remastered 2000” year display had been quietly showing nothing but file-tag years for six weeks.

Recovery — tools/relink_overrides_to_localfs.py works in two deliberately different modes: old-port LocalFs URLs carry a stable track id, so those rows are repointed whole (an exact same-file match); AssetUPnP-era orphans are matched by normalised artist + title and only the year is transplanted — the old artist/album/title fields are dropped on purpose, because they were mostly stale AcoustID-era values that would re-mask beets’ file tags on the next rescan. Existing overrides always win; the run is idempotent.

The apply run healed 46 rows whole and transplanted 8,087 orphans onto 8,009 live URLs. Live manual overrides went 31 → 7,976; the recovered years were visible in the API immediately, no restart needed. Spot-checks were textbook:

Findings 3 & 4 · Closed the other way

Pruned, and one honest loss

  • 650 orphaned “notfound” rows — sticky-negative markers for URLs that can never come back. Pruned by the same relink run.
  • 744 playlist rows removed by the 2026‑05‑31 playlist relink are unrecoverable: no pre-relink backup survives (the oldest on disk post-dates it), and the pre-2.0 project directory is gone. Time Machine is the only remaining avenue, if it ever matters. Current playlists are healthy — 835 rows, zero dead URLs.

Part II · Plan · proposed 12 July 2026 · P1+P2 shipped 13 July

Audiobooks: playback with cross-session resume

Play audiobooks through the gateway — in the PWA, on the Naim, and in CarPlay — and always pick up where the last listening session stopped, on any device. The design reuses the LocalFs machinery almost wholesale; the genuinely new piece is one small table and the discipline of writing to it.

Status (2026-07-13): P1 + P2 are live — the collection at /Volumes/SAMDATA-1TB/Audio_Books scanned as 11,548 chapters across 509 books (52 s first pass, 163 malformed files skipped), the source picker shows 💾 RoHaAudioBooks next to the music library, and the resume round-trip is verified end-to-end in the live PWA (“▶ Resume · Ch 1 — 5:21”). Two multi-root safety fixes landed en route: the shared scan cache is now scoped per root (each provider’s rescan would otherwise purge the other’s rows), and secondary-root track ids are namespace-salted (identical relative paths under two roots would collide on stream ids). One layout discovery: 11 books are single files at the library root (album_key='') — their positions key by file URL so they don’t share one resume row. P3 (Naim seek), P4 (CarPlay bookmarks) and P5 (chapter atoms, shelf) remain as planned below. P6 (OpenLibrary metadata — series/author/title overlay) shipped the same day; see the phases table.

Shape · one decision drives everything

A second LocalFs library, not a new subsystem

Audiobooks become a second LocalFs provider instance over their own root (e.g. /Volumes/SAMDATA/Audiobooks), with their own UDN — exactly the pattern the source picker, per-UDN browse, per-UDN search, and per-UDN radio were built for. A book is a folder (album_key), its chapters are the tracks, chapter order is filename order. Nothing about streaming, art, browse, or the Naim path is new.

  • Why a separate root + UDN, not a subfolder of Music: books must never surface in the music letter bar, in 📻 radio shuffle (play-count bias would keep proposing “Chapter 12”), or in music search. Per-UDN isolation gives all of that for free — the SRC picker already shows a 💾 entry per uuid:localfs-* source.
  • Why not a separate table (the videos pattern): videos needed different metadata (GPS, posters, persons). Audiobooks are audio — chapters stream through /localfs/stream, get Range support, DLNA headers, and browser-proxy behaviour identical to music. Duplicating that path would be pure cost.
  • Infrastructure already in place: the file server takes multiple allowed_roots (the video root is the precedent), UDNs are derived from the root path so a second instance can’t collide, and maybe_start_localfs() just needs to loop over configured roots.

Format note: .m4b joins AUDIO_EXTENSIONS (MIME audio/mp4, same as .m4a). Browser playback is safe; whether the Naim accepts m4b/AAC must be tested on day one — if it refuses, books are PWA + CarPlay features first and the Naim keeps music (no transcoding; that rule stands).

Data model · the new piece

One row per book: playback_positions

Resume state is per book, not per chapter — one row holding “which chapter, how far in.” Keyed by the book’s folder identity so it follows the same survival contract as play_counts / lyrics / album_art: a rebuild-index or clear(udn) never forgets where you are in a book.

CREATE TABLE IF NOT EXISTS playback_positions (
    album_key    TEXT PRIMARY KEY,   -- the book = its folder (survives re-index)
    url          TEXT NOT NULL,      -- chapter file last playing
    position_sec REAL NOT NULL,      -- offset within that chapter
    duration_sec REAL,               -- chapter duration at save time (progress %)
    finished     INTEGER NOT NULL DEFAULT 0,
    updated_at   INTEGER NOT NULL
);
  • Finished logic: saving a position within the last 60 s of the last chapter sets finished=1; the next resume offers “start over” instead. Re-listening clears the flag.
  • Write policy: last-writer-wins by updated_at — correct for a single listener moving between phone, desktop, and car.
  • Orphan behaviour: if a book’s folder is renamed, its row orphans harmlessly (same trade-off as play_counts); the book restarts from zero.

LibraryDB methods: position_set / position_get / position_clear / positions_list (the list powers a “continue listening” shelf, newest first, with progress %).

Flows · how resume actually happens

Three playback paths, one table

PathPosition savesResume
Browser / PWA app.js posts POST /api/position every ~20 s while playing, plus on pause, on track end, and on visibilitychange via sendBeacon (survives tab close / phone lock). Book header shows “▶ Resume · Ch 7 — 12:34” when a row exists; tapping queues from the saved chapter and sets audio.currentTime once metadata loads.
Naim / UPnP The RendererQueue monitor already polls GetPositionInfo every 2 s — when the playing track’s UDN is the audiobooks source, it persists the position every ~15 s server-side. Zero new polling. Queue chapters from the saved index; after Play, a new avtransport_seek() (AVTransport Seek, Unit=REL_TIME) jumps to the offset.
CarPlay / Subsonic Implement the Subsonic bookmark methods (getBookmarks / createBookmark / deleteBookmark) mapped onto playback_positions, and savePlayQueue / getPlayQueue for clients that sync their queue instead. Which of the two Amperfy actually uses gets verified against the real client before building both.

Endpoints (native, ASGI): POST /api/position (clamped payload, upserts), GET /api/position?album_key=, GET /api/positions (the shelf). All three stay off the Service Worker’s CACHEABLE_API allowlist — position data is live state and defaults to network-only, so no SW change is needed.

UX · small, deliberate

What the listener sees

  • Source picker: a 💾 “Audiobooks” entry appears automatically next to the music source. Books browse as folder-albums, chapters as tracks — the UI already knows how to draw all of it.
  • Resume button in the book header (the “▶ Play all” slot), with chapter + timestamp; “start over” when finished.
  • Continue-listening shelf: the ⭐ letter-bar pattern re-used — a 📖 entry listing in-progress books with a progress bar per book.
  • Playback speed (browser path only): 0.8×–2.0× via audio.playbackRate, persisted in localStorage. Explicitly out of scope for the Naim (no UPnP rate control) — and irrelevant to the bit-perfect rule, which is about bytes, not narration pace.
  • MediaSession: lock-screen shows book cover (folder art via the existing /art proxy), chapter title, and working prev/next — already wired for music, inherited for free.

Considered and rejected

Paths not taken

  • Books inside the music library — rejected: pollutes radio shuffle, the letter bar, and search; “what am I in the middle of” and “shuffle my music” are opposite retrieval modes.
  • A dedicated audiobooks table (the videos pattern) — rejected: chapters are plain audio; the entire stream/art/browse path would be duplicated for no new capability.
  • Client-side-only positions (localStorage / Amperfy’s own memory) — rejected: the whole point is resuming across devices; the gateway owns the single source of truth, clients report into it.
  • Per-chapter position rows — rejected: “furthest point in the book” is the semantic; per-chapter rows invite ambiguity about which chapter is current.

Open questions for day one: does the Naim accept m4b/AAC over AVTransport (test with one file before building P3)? Which resume mechanism does Amperfy actually call — bookmarks, play-queue, or neither? Both answers shape P3/P4 scope, neither blocks P1/P2.
